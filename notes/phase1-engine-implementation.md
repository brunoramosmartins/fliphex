# Phase 1 — Game Engine (implementation notes)

**Objective.** A correct, tested, performant engine — the substrate for all
three axes. Exit criterion is the test suite, not a document.

**Dates.** None — sequenced by dependency. Opened 2026-07-25.

**Governing decisions.** Read before writing code:
[adr-002](../docs/adr/adr-002-coordinate-system.md) (axial internal, `A1`–`E5`
external, flat 25×6 adjacency), [adr-003](../docs/adr/adr-003-piece-representation.md)
(6-bit masks; search state stores only a colour per cell + hand bitmasks — never
tile identity or rotation), [adr-006](../docs/adr/adr-006-no-chain-reaction.md)
(flips never chain, depth exactly 1). The canonical tables live in
[board-geometry.md](../docs/board-geometry.md) and
[piece-archetypes.md](../docs/piece-archetypes.md), both generated by
`scripts/`. **The engine must reproduce them exactly** — tests import the
generators and assert agreement (risk R12).

Implementation order follows the dependency chain:
`board → piece → state → moves → rules → notation → agents → tests`.

## board.py — Board, 25 cells, adjacency

Axial internals; build the flat `25×6` neighbour table once from
`scripts/gen_board_geometry.py`'s logic (or import it) and freeze it. Off-board
= sentinel (`-1`/`None`). Must support reduced variants later (Phase 3), so
parameterise `(n_cols, cells_per_col)` rather than hardcoding 5×5.

## piece.py — archetypes, rotation

Arrow pattern = 6-bit mask; rotation `k` = circular shift; the 12 archetypes as
module constants. **Deduplicate rotations** — orbit sizes are not all 6 (`P6`=1,
`P3-tri`=2, opposite-pair=3). Assert orbit sizes against `piece-archetypes.md`.

## state.py — immutable hashable GameState

Per adr-003: `(cell_colours[25], hand_p1_mask, hand_p2_mask, to_move)` for
search; separate append-only `history[]` (cell, archetype, rotation) for
notation/replay/H5 only — hot code never reads it. Zobrist keyed on
`(cell, colour)` and `(player, tile)`. `apply_move` returns a new state (undo =
keep the old reference).

## moves.py — generation, flip, terminal

Legal moves = empty cell × tile in hand × **distinct** rotation. Flip rule:
unconditional, one deep, never chained (adr-006); same-colour target is a no-op;
off-board arrows do nothing. Terminal = 25 plies / board full.

## rules.py — winner, score

`score` = cells per colour (sum 25); `winner` = higher count. Assert no draw
(25 odd) — a draw is a bug.

## notation.py — string encoding

`A1`–`E5` for cells (adr-002). Encode a full game (move list) and a single
state, round-trippable, for logs and shareable puzzles.

## agents — random, heuristic

`random_agent`: uniform over legal moves. `heuristic_agent`: greedy — maximise
pieces flipped this ply, ties broken randomly. Shared `Agent` interface.

## test suite

Per [engineering.md](../docs/engineering.md): adjacency + symmetry + all 16
border cells, rotation orbits, flip logic + non-chaining, invariants I1–I6 after
every ply of random games, joker rules, termination in exactly 25 plies, no
draws, 1000 random games clean. Tests import the doc generators and assert the
engine matches. **House rule: create tests, do not run them — the author runs
`pytest` / `ruff`.**

## Lessons Learned

A tested engine and a legible way to *see* the game are not optional
scaffolding — they are what let me trust everything built on top of them. The
highest-leverage thing I did this phase was, before writing any search or
learning code, to sit down and play the game by hand against myself, knowing the
outcome I expected, and check that the engine reproduced it move by move. That
turned rule validation from an abstract worry into something concrete I could
verify. The lesson generalises: for a project whose whole value rests on the
correctness of one small core, invest early in the tools that make that core
observable.

## Failed Attempts

My Phase 0 flip rule was wrong, and only hand-play revealed it. I had modelled a
flip as *assigning* the placing player's colour, so an arrow pointed at your own
tile did nothing. But the physical tiles are two-sided: a flip *turns the tile
over*, inverting its colour, so it can even cost you your own pieces. I found
this in Phase 1 by playing, not by testing — my tests faithfully checked the
wrong rule, which is exactly why tests alone were not enough. Catching it here,
before any solver run or network training, spared the project from learning a
corrupted game and burning compute on meaningless simulations. It is the
concrete reason "play the game before training anything" earned a place in the
plan.
